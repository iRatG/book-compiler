# Аргументы и доказательства

## ARG-001: Когда код становится легаси - экспоненциальный рост затрат

**Аргумент:** Каждая новая фича в старом коде требует все больше времени на понимание и модификацию.

**Доказательство из практики:**
- Версия 1: Добавить новую функцию за 1 день
- Версия 5: Та же функция требует 2 дня (нужно понять существующий код)
- Версия 10: Та же функция требует неделю (слишком много зависимостей)

**Почему это происходит:**
1. Первоначальный дизайн был простой
2. Каждая новая фича "прилеплялась" к существующей архитектуре
3. Когда достигается критическая сложность, любое изменение требует рефакторинга половины системы

**Научная основа:**
- Когнитивная нагрузка растет экспоненциально, а не линейно
- Кривая сложности: сначала пологая, потом резко взлетает

**Tags:** #legacy-code, #cost-of-change, #complexity-growth, #technical-debt

## ARG-002: Код, который умещается в голове, снижает ошибки в 10+ раз

**Аргумент:** Если функция или модуль понятны целиком, ошибок будет значительно меньше.

**Механизм:**
- При чтении понятного кода разработчик может построить полную ментальную модель
- При чтении сложного кода мозг переполняется, внимание перепрыгивает с места на место
- Невнимательность → пропуск importante деталей → ошибки

**Эмпирическое наблюдение:**
- Код с цикломатической сложностью < 5: ошибок практически нет
- Код с цикломатической сложностью 5-10: видны ошибки в коде-ревью
- Код с цикломатической сложностью > 15: каждое изменение вводит новые баги

**Tags:** #bug-prevention, #code-quality, #complexity-metrics, #error-rate

## ARG-003: Чек-листы работают, потому что превращают знание в действие

**Аргумент:** Опытный пилот самолета не "вспоминает" чек-лист во время полета - выполняет его автоматически. Это экономит в критических ситуациях.

**Исторический пример:**
- В 1930-х годах самолет B-17 был настолько сложен, что пилоты часто ошибались и падали даже с исправным самолетом
- Инженеры создали чек-лист предполетной проверки
- Результат: ошибки упали на 90%

**Применение к коду:**
- Чек-лист перед коммитом: прогнал ли я тесты? Проверил ли я форматирование?
- Чек-лист для код-ревью: расматрены ли граничные случаи? Хорошие ли имена переменных?
- Чек-лист для новой кодовой базы: настроен ли Git? Включены ли все ошибки компилятора?

**Психология:**
- Человеческая память ненадежна
- Чек-лист превращает знание (в голове) в действие (в истории Git)

**Tags:** #checklists, #quality-gates, #discipline, #error-prevention, #human-factors

## ARG-004: Инкапсуляция - это контракт между кодом и его читателем

**Аргумент:** Когда класс защищает свои инварианты (свойства, которые всегда верны), читатель может полагаться на эти гарантии.

**Пример - класс Money:**

```csharp
// Плохо: нет защиты инвариантов
public class Money {
    public decimal Amount; // Может быть отрицательным!
    public string Currency; // Может быть null!
}

// Хорошо: инварианты защищены
public class Money {
    private decimal amount;
    private string currency;
    
    public Money(decimal amount, string currency) {
        if (amount < 0) throw new ArgumentException("Amount cannot be negative");
        if (currency == null) throw new ArgumentNullException(nameof(currency));
        
        this.amount = amount;
        this.currency = currency;
    }
    
    public decimal Amount => amount; // Readonly
    public string Currency => currency; // Readonly
}
```

**Следствие:**
- Читатель кода может спать спокойно, зная, что Money никогда не будет иметь отрицательное значение
- Не нужно везде проверять `if (money.Amount >= 0)`

**Tags:** #encapsulation, #invariants, #contracts, #defensive-programming, #object-design

## ARG-005: Вертикальный срез выявляет ошибки дизайна раньше

**Аргумент:** Если вы разрабатываете слой за слоем (сначала модели, потом контроллеры), вы можете недостаточно хорошо спроектировать интерфейсы. Вертикальный срез выявляет это рано.

**Сценарий - Резервирование ресторана:**

**Послойный подход (BAD):**
1. Месяц 1: Разработчик A создает модели BankAccount, Reservation, Restaurant
2. Месяц 2: Разработчик B создает API контроллеры
3. Месяц 3: Команда встречается и понимает - контроллеры не подходят к моделям

**Вертикальный срез (GOOD):**
1. День 1: От HTTP запроса до сохранения в БД - работает одна маленькая фича
2. День 2: Вся команда видит работающий код, обсуждает дизайн
3. Недели 2-8: Расширяют вертикальный срез, добавляют новые фичи

**Преимущество:**
- Ошибки выявляются в день 1, а не в месяц 3
- Вся команда видит одно и то же состояние кода

**Tags:** #vertical-slice, #early-feedback, #agile-development, #integration, #api-design

## ARG-006: Тестирование "снаружи внутрь" дает лучший дизайн API

**Аргумент:** Если вы сначала напишете тест, который вызывает код так, как вы его хотите использовать, то API получится удобным.

**Пример - бронирование столика:**

```csharp
// Сначала пишем ИНТЕГРАЦИОННЫЙ тест (вызвав из HTTP)
// Это показывает, как код будет использован
[Fact]
public void ReserveTable_WithValidRequest_ReturnsOk() {
    var request = new ReservationRequest {
        Date = new DateTime(2024, 1, 15),
        Name = "John Doe",
        PartySize = 4
    };
    
    var response = controller.MakeReservation(request);
    
    Assert.Equal(200, response.StatusCode);
}

// Потом пишем UNIT тесты для деталей
// Потом пишем код
```

**Преимущество:**
- API рождается из использования, а не из фантазии
- Если тест сложно писать, значит API плохой

**Tags:** #test-driven-development, #outside-in, #api-design, #testability

## ARG-007: Коммиты с хорошими сообщениями - это документация кода

**Аргумент:** Вместо того, чтобы писать длинные комментарии, пишите понятные коммиты. История Git становится рассказом о том, почему код выглядит так.

**Плохой коммит:**
```
Fix bug
```

**Хороший коммит:**
```
Fix off-by-one error in DateRange validation

The method was checking if date <= end instead of date < end,
causing out-of-range dates to be accepted.

Fixes #1234
```

**Почему это работает:**
- Через неделю вы забудете, почему вы изменили эту линию кода
- Через месяц новый разработчик спросит "почему это так странно?"
- История Git показывает ответ

**Tags:** #git-discipline, #documentation, #commit-messages, #knowledge-transfer

## ARG-008: Парное программирование снижает ошибки и распространяет знание

**Аргумент:** Когда два разработчика пишут код вместе, они быстро найдут ошибки и оба поймут, как это работает.

**Научное обоснование:**
- Исследования показывают, что парное программирование снижает количество ошибок на 15-20%
- Время разработки увеличивается на 5-10%, но общее время (разработка + исправление ошибок) уменьшается
- Знание распределяется между двумя людьми вместо одного

**Организационное преимущество:**
- Если один разработчик уходит, знание не уходит с ним
- Новичок быстрее учится, работая с опытным
- Меньше "королей кода" (знают только они)

**Tags:** #pair-programming, #code-quality, #knowledge-sharing, #team-dynamics

## ARG-009: Refactoring модульных тестов - это инвестиция в устойчивость

**Аргумент:** Тесты - это код, который читается и пишется. Если тесты плохо написаны, они замораживают разработку.

**Проблема:**
- Новый разработчик может разломать 50 тестов, изменив одну функцию
- Если тесты хрупкие (зависят от деталей реализации, а не от поведения), изменение всегда их ломает
- Результат: разработчики начинают игнорировать тесты или удалять их

**Решение:**
- Рефакторьте тесты как продакшен-код
- Используйте правильные шаблоны (AAA, Given-When-Then)
- Тесты должны проверять поведение, а не реализацию

**Tags:** #test-quality, #test-refactoring, #maintainability, #brittle-tests

## ARG-010: Метод бисекции находит баг в O(log n) попытках

**Аргумент:** Если в коде есть баг, введенный за последние 100 коммитов, вы можете найти его за ~7 попыток (log2(100)).

**Механика:**
```
100 коммитов
  |
  +-- Попытка 1: проверяю 50-й коммит. Баг есть? Нет.
           |
           +-- Попытка 2: проверяю 75-й коммит. Баг есть? Да.
                    |
                    +-- Попытка 3: проверяю 62-й. Баг есть? Да.
                         [продолжаем...]
```

**Git интеграция:**
```bash
git bisect start
git bisect bad  # текущий коммит плохой
git bisect good v1.0  # этот коммит хороший
# Git автоматически прыгает к середине
git bisect bad # или git bisect good
# Повторяем, пока не найдем exact коммит
```

**Tags:** #debugging, #git-bisect, #binary-search, #bug-finding, #efficiency

# Ключевые идеи и принципы

## ПРИНЦИП 1: Эвристики важнее правил

**Утверждение:**
Вместо жестких правил ("максимум 80 символов в строке") используйте эвристики ("код должен быть удобен для чтения").

**Почему это важно:**
- Правила создают ложное чувство уверенности
- Эвристики требуют суждения и понимания контекста
- Опытный разработчик использует эвристики интуитивно, новичок - учится их применять

**Практический смысл:**
- Это книга о том, как думать и решать, а не о том, что делать

**Tags:** #heuristics, #judgment, #context-aware, #practical-wisdom

---

## ПРИНЦИП 2: Код читается больше, чем пишется

**Утверждение:**
Разработчик тратит 90% времени на чтение и понимание кода, 10% на написание.

**Следствия:**
- Оптимизируйте для читаемости, а не для скорости написания
- Понятность важнее краткости
- Четкие имена переменных стоят больше, чем экономия символов

**Tags:** #readability, #code-comprehension, #writer-reader-asymmetry

---

## ПРИНЦИП 3: Когнитивная нагрузка - главный враг

**Утверждение:**
Человеческий мозг может удерживать в рабочей памяти только ~7-9 концепций одновременно.

**Практические следствия:**
- Функция, требующая понимания 50 переменных - это враг
- Лучше иметь 20 маленьких функций, чем одну большую сложную
- Инкапсуляция - это способ снизить когнитивную нагрузку на читателя кода

**Tags:** #cognitive-load, #memory-limits, #mental-model, #code-complexity

---

## ПРИНЦИП 4: Инкапсуляция - это защита инвариантов

**Утверждение:**
Инкапсуляция - не просто "скрыть приватное", а защита неизменяемых свойств объекта (инвариантов).

**Пример:**
Класс `Money` с полями `amount` и `currency` должен гарантировать, что:
- `amount` никогда не отрицательное
- `currency` никогда не `null`

**Это значит:**
- Класс проверяет эти условия при создании и модификации
- Внешний код может полагаться на эти гарантии

**Tags:** #encapsulation, #invariants, #contracts, #object-design

---

## ПРИНЦИП 5: Декомпозиция - это уменьшение когнитивной нагрузки

**Утверждение:**
Разделяйте большие функции на маленькие не ради "правил", а чтобы читатель понимал каждый кусок отдельно.

**Метрика сложности:**
- Цикломатическая сложность (количество условных ветвлений)
- Правило 80/24: функция не должна быть больше 80 символов ширины на 24 строки высоты

**Tags:** #decomposition, #cyclomatic-complexity, #function-size, #modularity

---

## ПРИНЦИП 6: Вертикальный срез лучше, чем послойная разработка

**Утверждение:**
Вместо разработки "сначала все модели, потом все контроллеры" делайте вертикальные срезы: от пользовательского ввода до сохранения в БД.

**Почему:**
- Вы быстро получаете работающее ПО
- Видите ошибки дизайна рано
- Вся команда видит тот же "ходячий скелет"

**Tags:** #vertical-slice, #agile-development, #working-software, #iterative-design

---

## ПРИНЦИП 7: Тестирование "снаружи внутрь" (outside-in)

**Утверждение:**
Начните с интеграционного теста (как будет использован код), потом пишите код для его прохождения.

**Отличие от TDD:**
- TDD: unit тест → код → рефакторинг
- Outside-in: интеграционный тест → unit тесты → код

**Преимущество:**
- Сразу видно, нужен ли вам код
- API дизайн рождается из использования, не из идей в воздухе

**Tags:** #test-driven-development, #outside-in, #behavior-driven, #api-design

---

## ПРИНЦИП 8: API дизайн - это дизайн вызывающего кода

**Утверждение:**
Хороший API - это тот, который удобно вызывать, не заставляет запоминать порядок параметров или читать документацию каждый раз.

**Техники:**
- **Affordance** (возможность): по названию и сигнатуре должно быть ясно, как использовать
- **Poka-Yoke** (защита от ошибок): сложно вызвать неправильно
- **CQS** (Command Query Separation): команды меняют состояние, запросы - нет

**Tags:** #api-design, #usability, #affordance, #type-safety

---

## ПРИНЦИП 9: Чек-листы спасают жизни

**Утверждение:**
Чек-листы не для новичков, а для экспертов. Они превращают знание в привычку.

**Примеры из книги:**
- Чек-лист для новой кодовой базы (Git, автоматизация сборки, сообщения об ошибках)
- Чек-лист перед коммитом
- Чек-лист код-ревью

**Tags:** #checklists, #quality-gates, #discipline, #habituation

---

## ПРИНЦИП 10: Коллективное владение кодом требует инструментов и дисциплины

**Утверждение:**
Нельзя просто сказать "владеть кодом вместе" - нужны Git, code review, парное программирование, ясные коммиты.

**Инструменты:**
- **Git**: правильные сообщения коммитов, маленькие коммиты
- **CI/CD**: каждый коммит должен пройти все тесты
- **Code Review**: обязательная проверка перед слиянием

**Tags:** #collective-ownership, #git-discipline, #code-review, #continuous-integration

---

## ПРИНЦИП 11: Для расширения большого кода используйте паттерны

**Утверждение:**
Когда нужно добавить новую функцию в легаси-код, используйте проверенные паттерны, а не переписывайте все.

**Паттерны:**
- **Strangler Pattern** ("Душитель"): постепенно вводи новый код, задушив старый
- **Feature Flags**: новые фичи скрыты под флагом до полной готовности

**Tags:** #legacy-code, #refactoring, #strangler-pattern, #feature-flags

---

## ПРИНЦИП 12: Рабочий процесс - это часть архитектуры

**Утверждение:**
Как вы организуете день, берете перерывы, пишете коммиты - все это влияет на качество кода.

**Тайм-боксинг:**
- Работайте сосредоточенно, но с перерывами
- Не зацикливайтесь на одной проблеме часами

**Закон Конвея:**
- Организационная структура отражается в архитектуре системы

**Tags:** #time-management, #focus, #work-habits, #organizational-structure

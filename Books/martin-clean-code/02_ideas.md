# Чистый код: Слой ИДЕИ

---

## Глава 1: Чистый код

**C-001:** Код пишется для людей, прежде всего, и только потом для машин  
**C-002:** Чистый код - это долг разработчика перед командой  
**C-003:** Скорость разработки прямо пропорциональна чистоте кода  

---

## Глава 2: Значимые имена

**C-004:** Имя переменной должно отвечать на все вопросы (зачем, что, как использовать)  
**C-005:** Плохие имена (a, x1, data) указывают на плохое понимание проблемы  
**C-006:** Одно слово в коде должно значить одно и то же везде (не mix customer/client)  
**C-007:** Избегать диезинформации: accountList не должен быть не-List  

Пример:
```
// Плохо:
List<int[]> list1 = new ArrayList();

// Хорошо:
List<Cell> flaggedCells = new ArrayList();
```

---

## Глава 3: Функции

**C-008:** Функция должна делать одно и делать его хорошо (Single Responsibility)  
**C-009:** Функция должна быть маленькой (вмещаться на экран)  
**C-010:** Небольшое количество параметров (макс 3-4)  
**C-011:** Функция либо что-то делает, либо что-то возвращает (не оба)  

Нарушение: функция, которая скрывает побочные эффекты.

---

## Глава 4: Комментарии

**C-012:** Чистый код не нуждается в комментариях  
**C-013:** Комментарий должен объяснять "почему", а не "что" (что видно из кода)  
**C-014:** Удалять старые комментарии - это уборка  
**C-015:** Документация в коде лучше, чем в Wiki  

Плохой комментарий: `// увеличиваем счетчик` (это видно из кода)  
Хороший комментарий: `// ++i вместо i++ потому что в цикле не нужна временная переменная`

---

## Глава 5: Форматирование

**C-016:** Форматирование - это общение  
**C-017:** Вертикальная плотность должна отражать концептуальную близость  
**C-018:** Методы одного класса должны быть вместе  
**C-019:** Горизонтальное выравнивание помогает читать (интервалы после запятых)  

---

## Глава 6: Обработка ошибок

**C-020:** Обработка ошибок - это функция программы, не добавок  
**C-021:** Использовать исключения вместо кодов ошибок  
**C-022:** Заворачивать сторонние исключения в свои (абстракция)  
**C-023:** Не возвращать null, не передавать null  

---

## Глава 7: Модули

**C-024:** Модуль должен скрывать детали реализации  
**C-025:** Публичные переменные - это запах кода  
**C-026:** Тайная зависимость между модулями хуже, чем явная  

---

## Глава 8: Границы

**C-027:** Третья сторона код должна быть обёрнута  
**C-028:** Learning Tests - пишу тесты для чужого API, чтобы понять его  
**C-029:** Логирование и тестирование - это не обязанность автора библиотеки  

---

## Глава 9: Unit Tests

**C-030:** Тесты - это первый код, который использует API  
**C-031:** TDD (Test-Driven Development) дает уверенность в коде  
**C-032:** Тест должен быть чистым, как и production-код  

---

## Глава 10: Classname, Method Name, Argument

**C-033:** Имя класса должно быть существительным  
**C-034:** Имя метода должно быть глаголом  
**C-035:** Аргументы - это шум, минимизировать их число  

---

## Глава 11: Параллелизм

**C-036:** Многопоточность создает сложность  
**C-037:** Keep it simple, separate concerns  
**C-038:** Синхронизация должна быть явной  

---

## Глава 12: Появление

**C-039:** Код может быть чистым в процессе разработки и грязным после  
**C-040:** Refactoring - это инструмент для поддержания чистоты  

---

## Глава 13: Запахи и эвристики

**C-041:** Дублирование кода (DRY - Don't Repeat Yourself)  
**C-042:** Слишком много уровней абстракции  
**C-043:** Неправильные границы классов/функций  

---

## Главы 14-17: Практика

**C-044:** Рефакторинг - это процесс улучшения кода без изменения функциональности  
**C-045:** Даже чистый код можно сделать чище  
**C-046:** Процесс: понять → улучшить → протестировать → повторить  

---

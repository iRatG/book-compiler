**Статус:** Основная концепция знания  

---

## Определение

**Архитектура** — это набор решений, определяющих форму системы, где важность каждого решения определяется стоимостью его изменения.

Архитектура — это не отдельная от кода деятельность. Архитектура пронизывает весь код, от высокоуровневой структуры до выбора переменных внутри функции.

---

## Как разные авторы видят архитектуру

### 1. Clean Architecture (Роберт Мартин)

**Основной тезис:** Архитектура — это набор решений, которые вы хотели бы принять рано, но которые не более вероятны, чем другие.

**Ключевые идеи:**
- Архитектура = дизайн (нет разницы)
- Цель архитектуры: минимизировать человеческие трудозатраты на создание и поддержку системы
- Архитектура обслуживает две ценности: **поведение** (urgent, не always important) и **структура** (important, не always urgent)
- Должны защищать архитектуру против давления бизнеса

**Инструменты:**
- Три парадигмы программирования (structured, OOP, functional)
- Полиморфизм для разделения зависимостей
- Четкие границы между компонентами

**Ссылка:** [Clean Architecture → 02_ideas.md → ПРИНЦИП 1-2](../../Books/clean-architecture/02_ideas.md)

---

### 2. Идеальная работа (Роберт Мартин)

**Основной тезис:** Архитектура — это выбор, который вы делаете как профессионал с этической ответственностью.

**Ключевые идеи:**
- Архитектура как проявление мастерства
- Правильная архитектура позволяет быстро добавлять фичи
- Плохая архитектура останавливает разработку
- Выбор технологии — это архитектурное решение с долгосрочными последствиями

**Инструменты:**
- TDD как дисциплина для хорошей архитектуры
- Рефакторинг для улучшения архитектуры
- Смелость сказать "нет" плохой архитектуре

**Ссылка:** [Идеальная работа → 02_ideas.md → ПРИНЦИП 3, 8](../../Books/ideal-work/02_ideas.md)

---

### 3. Идеальный программист (The Pragmatic Programmer)

**Основной тезис:** Архитектура — это стратегия долгосрочного развития, которую нужно защищать.

**Ключевые идеи:**
- Плохая архитектура замораживает прибыль (растущие затраты на разработку)
- Профессионализм — это борьба за архитектуру против менеджмента
- Архитектура начинается с первого дня, не "позже"

**Инструменты:**
- Estimation как способ показать cost-of-change
- Code review как защита архитектуры
- Автоматизация как инвестиция в архитектуру

**Ссылка:** [Идеальный программист → 02_ideas.md → ПРИНЦИП 2, 5](../../Books/pragmatic-programmer/02_ideas.md)

---

### 4. Код, который умещается в голове (Code That Fits in Your Head)

**Основной тезис:** Архитектура — это выбор, что скрыть от внимания программиста, чтобы остальное помещалось в голову.

**Ключевые идеи:**
- Архитектура должна снижать когнитивную нагрузку
- Правильная архитектура позволяет новому разработчику быстро разобраться
- API дизайн — это архитектурное решение
- Правильная структура файлов показывает намерение (screaming architecture)

**Инструменты:**
- Outside-in TDD для проектирования интерфейсов
- Паттерны для повторяемых решений
- Правильное именование как часть архитектуры

**Ссылка:** [Code That Fits → 02_ideas.md → ПРИНЦИП 4, 10, 12](../../Books/code-fits-in-head/02_ideas.md)

---

### 5. Модели параллельного программирования

**Основной тезис:** Архитектура включает выбор модели параллелизма (синхронный, асинхронный, actor-based, lock-free).

**Ключевые идеи:**
- Архитектура должна соответствовать проблеме (использовать правильную модель)
- Неправильная архитектура усложняет параллелизм
- Immutability — это архитектурное решение, решающее race conditions
- Масштабируемость — следствие правильной архитектуры

**Инструменты:**
- Выбор между shared-memory, message-passing, lock-free подходами
- Immutability для безопасности
- Правильное разделение ответственности между потоками

**Ссылка:** [Parallel Programming → 02_ideas.md → ПРИНЦИП 1, 3](../../Books/parallel-programming/02_ideas.md)

## Пересечения

### Clean Architecture ↔ Code That Fits
- Оба подчеркивают, что архитектура — это **решения, которые влияют на стоимость**
- Оба защищают границы компонентов
- Оба говорят о том, что архитектура должна быть видна в коде

### Идеальная работа ↔ Идеальный программист
- Оба видят архитектуру как **профессиональную ответственность**
- Оба говорят о борьбе за качество против давления
- Оба видят долгосрочный вред плохой архитектуры

### Clean Architecture ↔ Параллельное программирование
- Оба видят архитектуру как **выбор модели**
- Оба подчеркивают важность **разделения ответственности**
- Оба говорят что правильная архитектура масштабируется, неправильная — нет

## Практические выводы

### 1. Архитектура — это инвестиция, не расход
Выбрать хорошую архитектуру на 20% медленнее сейчас, но экономит 80% затрат потом.

**Где об этом:**
- Clean Architecture: Принцип 2 (стоимость-изменений)
- Ideal Work: Консеквенс 2 (TDD как инвестиция)
- Pragmatic Programmer: Аргумент 3 (парадокс спешки)

### 2. Архитектура должна быть видна в коде
Если посмотреть на структуру файлов, должно быть понятно, что делает система.

**Где об этом:**
- Code That Fits: Принцип 10 (screaming architecture)
- Clean Architecture: Консеквенс 5 (организация по доменам)

### 3. Архитектура — это набор границ
Задача архитектуры — определить границы компонентов так, чтобы их было легко менять независимо.

**Где об этом:**
- Clean Architecture: Принцип 2, Аргумент 7
- Code That Fits: Принцип 7, Консеквенс 2

### 4. Архитектура должна соответствовать проблеме
Нет универсальной архитектуры. Правильная архитектура зависит от вида системы и её ограничений.

**Где об этом:**
- Parallel Programming: Принцип 1, 3
- Code That Fits: Консеквенс 12 (выбор между монолитом и микросервисами)

## Противоречия

### Есть ли противоречия между авторами?

**Нет основных противоречий.** Все авторы согласны:
1. Архитектура важна
2. Плохая архитектура стоит дорого
3. Архитектура должна служить изменяемости

**Разные акценты:**
- Мартин (Clean Architecture) — на парадигмах и структурных решениях
- Мартин (Ideal Work) — на этике и долгосрочном эффекте
- Pragmatic Programmer — на боевой готовности и давлении
- Seemann (Code That Fits) — на когнитивной нагрузке
- Fedotov (Parallel Programming) — на моделях и масштабируемости
